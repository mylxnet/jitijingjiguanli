# 多用户与权限控制改造方案

- 版本：v1.0（方案稿）
- 日期：2026-10-16
- 状态：待评审，未实施（不涉及任何代码改动）

---

## 1. 背景与目标

当前系统为「单一组织 + 单一管理员」模式：注册关闸后整个系统只有 1 个账号，该账号拥有全部权限，登录即可操作和重置一切数据。实际使用中，集体经贸账目通常需要多人协作（如会计、出纳、村干部查看），不同人的权责不同，需要一个账号体系来区分「谁能看、谁能改、谁能管理」。

**目标**（经逐项确认）：

1. 同一组织共享一套账本，不做数据隔离改动（现有 `org_id` 隔离保留不动）。
2. 账号由后台创建，**继续禁止开放注册**。
3. 三种角色（档位由高到低）：

| 角色 | 编码 | 定位 |
|---|---|---|
| 所有者 / 超管 | `owner` | 唯一，原管理员迁移而来；全功能 + 管理所有账号 + 最高危操作 |
| 高级用户 | `admin` | 全功能日常操作 + 管理一般用户 |
| 一般用户 | `viewer` | 只读：可查看业务数据、导出/下载（备份下载除外），不可写、不可进管理页 |

## 2. 现状盘点（代码级事实）

以下基于当前 `v0.24.1` 代码，逐条列出现状与需改动点：

| # | 现状 | 位置 | 对目标的影响 |
|---|---|---|---|
| 1 | 已有多组织表 `org` / `user` / `session`，`org_id` 贯穿所有业务表 | `server/internal/platform/migrations/003_multi_org.sql` | 好消息：数据隔离骨架已具备，本方案**不动数据隔离** |
| 2 | `user` 表仅 `id, org_id, username(全局唯一), password_hash, created_at`，**无角色、无状态字段** | `server/internal/auth/model.go` | 需新增 `role` / `status` 列 |
| 3 | 注册即关闸：`CountUsers()>0` 拒绝再注册 | `server/internal/auth/service.go`（`RegisterOrg`、`IsRegistrationOpen`） | 保持不变，仅首个注册人改为 `owner` |
| 4 | 会话鉴权中间件 `RequireAuth` 只写入 `userID`/`orgID` 到上下文，**无角色** | `server/internal/auth/middleware.go` | 需扩展为把 `role` 一并写入上下文 |
| 5 | `/api/me` 硬编码返回 `userID/orgID/orgName/onboarded`，**无 role** | `server/cmd/server/main.go` | 需返回 `role` |
| 6 | `change_log` / 操作日志**无操作者字段** | `server/internal/changelog/model.go`、`.../migrations/003_multi_org.sql` | 多用户后无法区分「谁干的」，需新增 `operator` 列并回填写入 |
| 7 | 系统重置、恢复备份、清空日志等接口**仅要求登录，无角色判断** | `server/cmd/server/main.go`、`server/internal/changelog/handler.go` | 需挂 `owner` 角色 |
| 8 | 备份「下载文件」「立即备份」当前仅登录即可 | `server/cmd/server/main.go`（`registerBackupRoutes`） | 需挂 `admin`+
| 9 | 导出统一走 `GET /api/export` | `server/internal/export/handler.go` | 只读，`viewer` 可访问（保留） |

**结论**：数据隔离层无需改动，核心增量是「角色字段 + RBAC 中间件 + 接口分级 + 前端按角色收口 + 操作者留痕」。

## 4. 数据模型改造

### 4.1 新迁移 `021_user_roles.sql`

沿用现有迁移编号规则（`server/internal/platform/migrations/` 已到 `020`），新增 `021`：

```sql
-- 021_user_roles.sql — 多用户 + 角色权限（v0.25.0）
-- 设计依据：docs/27-多用户与权限控制方案.md

-- user 表新增角色与状态
ALTER TABLE user ADD COLUMN role TEXT NOT NULL DEFAULT 'viewer'
    CHECK (role IN ('owner','admin','viewer'));
ALTER TABLE user ADD COLUMN status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','disabled'));

-- 现有唯一管理员升级为所有者（当前系统最多 1 个用户，回填安全）
UPDATE user SET role = 'owner' WHERE role = 'viewer';

-- change_log 新增操作者（冗余用户名快照，账号删改后仍可追溯）
ALTER TABLE change_log ADD COLUMN operator TEXT;
```

要点：
- `role` 用三值枚举 `owner/admin/viewer`；`status` 用 `active/disabled`（软停用，不做物理删除避免破坏历史归属）。
- `operator` 采用**用户名冗余快照**而非外键，保证账号被删/改名后日志仍可读。
- `username` 仍保持全局唯一（现状），因当前为单组织部署，无冲突风险。

### 4.2 模型结构体更新

`server/internal/auth/model.go` 的 `User` 增加：

```go
Role   string `json:"role"`   // owner / admin / viewer
Status string `json:"status"` // active / disabled
```

`getter`/查询 SQL 同步补两个字段（`FindByUsername`、`FindUserByID`、`FindAnyUser` 等）。

## 5. 后端改造

### 5.1 auth 包：角色与中间件

1. **角色常量与服务端校验**（`server/internal/auth/service.go`）：
   - 新增 `RoleOwner = "owner"` / `RoleAdmin = "admin"` / `RoleViewer = "viewer"`。
   - `RegisterOrg` 首个注册用户角色写 `owner`（事务 `createUserTx` 增加 role 入参）。
   - `Login` 校验账号 `status`：`disabled` 账号拒绝登录（统一返回「账号或密码错误」，避免枚举），并返回 `role`。
   - `ResetPassword`（公开忘记密码）语义调整：因多用户后「重置任意用户」不安全，改为——仅当系统存在且**只有一个 `owner`** 时，重置该 owner 密码；否则返回明确错误。详见 §8 安全边界。

2. **`Resolve` 扩展**：会话校验时一并查出 `role`/`status`，写进 gin 上下文；`RequireAuth` 中间件同时写入 `ctxRoleKey`。

3. **新增 `CurrentRole(c)`**（`server/internal/auth/middleware.go`），与 `CurrentUserID`/`CurrentOrgID` 并列。

4. **新增两个角色中间件**：
   - `RequireRole(roles ...string)`：要求当前用户角色在允许列表内，否则 403。
   - `RequireWrite`：约定「非 GET/HEAD 一律视为写操作」，对 `viewer` 拒绝；内置白名单豁免自服务端点（见下）。

```go
// 伪码示例
func RequireWrite(svc *Service) gin.HandlerFunc {
    return func(c *gin.Context) {
        if c.Request.Method == "GET" || c.Request.Method == "HEAD" {
            c.Next(); return
        }
        // 白名单：登出、改自己密码对所有已登录用户放行
        if c.Request.Method == "POST" && c.Request.URL.Path == "/api/auth/logout" { c.Next(); return }
        if c.Request.Method == "PUT" && c.Request.URL.Path == "/api/auth/password" { c.Next(); return }
        if role := CurrentRole(c); role != RoleOwner && role != RoleAdmin {
            platform.Fail(c, 403, "FORBIDDEN", "当前账号无操作权限"); c.Abort(); return
        }
        c.Next()
    }
}
```

### 5.2 路由分级改造（`server/cmd/server/main.go`）

现路由全部挂在单层 `authed := r.Group("", auth.RequireAuth(...))` 下。改为四个组：

| 组 | 中间件 | 挂载内容 |
|---|---|---|
| `public` | 无 | `login/register/reset-password/registration-status`（不变） |
| `read` | `RequireAuth` | 仅 GET：`/api/me`、业务查询、`/api/export` |
| `write` | `RequireAuth` + `RequireWrite` | 业务写接口（`viewer` 已被拦截） |
| `admin` | `RequireAuth` + `RequireRole(admin, owner)` | 备份列表/立即备份/下载/删除、操作日志查看、用户管理 |
| `owner` | `RequireAuth` + `RequireRole(owner)` | 系统重置、恢复备份、清空操作日志 |

> 说明：`RequireWrite` 采用**组级别统一拦截**，绝大多数业务 handler 的写接口无需逐个加判断；只有 `admin`/`owner` 两组和 3 个 owner 端点需要显式挂中间件，改动面最小、漏网风险最低。

具体挂钩（依据已读代码）：

| 接口 | 归属组 | 依据 |
|---|---|---|
| `GET /api/export` | `read` | 只读，viewer 可导出 |
| `POST /api/auth/logout`、`PUT /api/auth/password` | `read`（经 RequireWrite 白名单放行） | 自服务 |
| `GET /api/backups`、`POST /api/backups`、`DELETE /api/backups/:id`、`GET /api/backups/:id/download` | `admin` | 备份管理 |
| `POST /api/backups/:id/restore` | `owner` | 覆盖数据 |
| `GET /api/operation-logs`、`GET /api/changelog` | `admin` | 查看操作日志 |
| `DELETE /api/operation-logs` | `owner` | 清空日志 |
| `POST /api/system/reset` | `owner` | 系统重置 |
| `GET /api/settings` | `read`（或 `admin`，见 §9 待确认） | 配置读取 |
| `PUT /api/settings` | `write` | 配置修改 |
| 各业务 handler（category/transaction/summary/fundmove/contract/receivable/onboarding） | `read`+`write` 拆分 | 由各组 `Register` 内部按方法分流 |

**handler 收敛方式**：现有每个 handler 的 `Register(r)` 内部同时挂 GET 与写方法，需把 `Register` 拆为 `RegisterRead(read)` 与 `RegisterWrite(write)` 两个（或让 `Register` 接收带 `RequireWrite` 的组并在内部对写路由二次鉴权）。推荐前者，语义清晰。

### 5.3 新增「用户管理」接口

新建 `server/internal/users/` 包（或并入 `auth` 包），挂 `admin` 组：

| 接口 | 允许角色 | 说明 |
|---|---|---|
| `GET /api/users` | admin, owner | 列出本组织用户（id/username/role/status/createdAt） |
| `POST /api/users` | admin, owner | 建号：admin 仅能建 `viewer`；owner 可建 `viewer`/`admin` |
| `PATCH /api/users/:id` | admin, owner | 改角色/启用禁用：admin 仅能操作 `viewer`；owner 可操作任何人（除自我降级限制） |
| `DELETE /api/users/:id` | admin, owner | 停用（软删，置 `disabled`）：不可自删、不可停用最后一个 `owner` |
| `POST /api/users/:id/reset-password` | admin, owner | 重置为初始密码 `admin888`（仅可操作 `viewer`；owner 可重置 admin） |

角色操作约束（后端强制校验，防越权）：
- `admin` 只能创建/管理 `viewer`，不能创建或改动任何 `admin`/`owner`。
- 不能对自己做「降级/停用/删除」，避免把系统锁死。
- 系统内 `owner` 数量不可归零：任何操作不得导致「无 owner」。

### 5.4 操作日志留痕（操作者）

- `change_log` 新增 `operator` 列（见 §4.1）。
- 在 `server/internal/changelog/` 的日志写入公共入口注入当前用户名快照（`auth.CurrentUsername(c)`，读取上下文时携带）。
- `OpLog` DTO 增加 `operator` 字段；前端「操作日志」弹窗展示「操作人」列。

### 5.5 `org` 表与引导页

- `onboarded` 引导流程属数据初始化（写操作），归 `admin`+（`RequireWrite` 已覆盖）；不做额外变更。

## 6. 前端改造

### 6.1 登录态与角色存储

- 登录成功与 `/api/me` 返回 `role` 后，写入本地状态（`localStorage.jt_role` 或 Vuex/Pinia，按项目现状）与全局态。
- `web/src/features/.../LoginPage.vue`：登录响应里读取 `role` 一并存下。
- 登出时清空角色。

### 6.2 路由守卫（`web/src/router`）

- 全局 `beforeEach`：根据 `role` 拦截：
  - 未登录 → 跳登录页（现状已有）。
  - `viewer` 访问 `/settings`、新增的 `/users` 等管理路由 → 重定向回看板并提示无权限。

### 6.3 侧边栏菜单收口（`web/src/features/.../SideNav.vue`）

- `设置`、新增的 `用户管理` 入口仅 `admin`/`owner` 可见。
- `viewer` 不显示任何写操作入口（如「记一笔」按钮、快速记账入口）。

### 6.4 写操作按钮隐藏

- 全局约定：一个 `v-permission="write"` 指令或 `isWritable` 计算属性，`viewer` 时隐藏/禁用所有增删改按钮（记一笔、新增、编辑、删除、作废、收缴、上传合同、改期、导入、保存等）。
- 管理页内部再按 `admin`/`owner` 细分：设置页中「系统重置」「恢复备份」「清除操作日志」仅 `owner` 可见/可点。

### 6.5 新增「用户管理」页（`web/src/features/.../UsersPage.vue`）

- 列表展示：用户名、角色、状态、创建时间。
- 操作：新建用户（用户名+初始密码+角色下拉，角色可选范围按当前账号身份收口）、启用/禁用、重置密码、删除（停用）。
- 交互遵循既有 UI 规范（统计卡风格、浅色按钮、二次确认弹窗、防误操作禁用等）。

### 6.6 操作日志弹窗

- 展示新增「操作人」列。

## 7. 数据迁移方案

1. 上线新版本时 `platform.Migrate` 自动执行 `021_user_roles.sql`（现有迁移链已支持顺序执行）。
2. **现有唯一 admin 自动变为 `owner`**，账本数据零改动、无需手工操作。
3. 系统重置（owner 专属）后：仍删除所有 user/org，回到「注册组织」流程，首个注册者仍为 `owner`（与现状注册语义一致）。

## 8. 安全边界与容错

1. **后端是权限的唯一权威**：前端隐藏只是体验，所有分级必须以接口层面的 `RequireRole`/`RequireWrite` 为准，确保绕过前端直接调接口也会被 403。
2. **`viewer=只读` 的硬约束**：`RequireWrite` 拦截所有非 GET；新增写接口必须挂进 `write` 组而非 `read`/`public` 组，否则视为漏网。
3. **禁用账号即时失效**：停用/删除账号时，删除其全部 `session`，强制下线。
4. **账号枚举防护**：登录失败、禁用账号登录统一返回「账号或密码错误」。
5. **最后一个 owner 保护**：不允许停用/删除/降级最后一个 `owner`。
6. **忘记密码语义收紧**：多用户后公开的 `/api/auth/reset-password` 不能再「重置任意用户」，改为「仅单 owner 时重置该 owner」，否则返回错误并提示联系管理员（见 §9 待确认）。
7. **操作者留痕完整性**：`operator` 为空的老日志显示「（系统/迁移前）」占位，不回填。
