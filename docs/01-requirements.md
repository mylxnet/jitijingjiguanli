> 本文件是后续 PRD、设计方案的**唯一事实来源**。所有假设必须显式标注，不得隐含。

## 项目一句话

为一个集体经济组织做**内部管理用的收支台账**，替代目前无固定格式的 Excel。
**单人记账、移动优先、局域网自托管。**

## 第 0 轮 · 锚定问题

**Q1. 目标形态？**
A: **参考它，从零自己写。** 自己选技术栈、自己实现，不吃它的代码。

**Q2. 给谁解决什么问题？**（首次回答后用户纠正）
A（初答）: 我个人 / 家庭自用。
A（**纠正，以本条为准**）: **不是家庭开支，是一个集体经济组织的账。主要是记录收支就行，账户一个，设可定义的二级科目。一人记账，暂时不要权限。**

**Q3. 现在的替代方案？**
A: Excel / 表格手工记，**没有固定格式，比较随意**。
→ 推论：历史数据迁移价值有限。**从某一时间点起建新账，旧 Excel 存档，不做导入。**

**Q4. 明确不做的事？**（初答）
A: 多币种/汇率、多人协作/共享账本、原生 App、导入导出。

> 「不做导入导出」经复议 **已推翻**，导出纳入 M5。详见决策记录 D2。

**Q5. 组织性质 / 制度约束？**（纠正后补问）
A: **只是内部管理台账。** 不对外报送、不经审计、**不受会计制度约束**。

> 调研结论（已核实，供未来性质变更时引用）：
> - 《农村集体经济组织会计制度》（财会〔2023〕14号）2024-01-01 施行，废止财会〔2004〕12号。
> - 规定借贷记账法、42 个全国统一编号的一级科目、四张法定报表（科目余额表、收支明细表、资产负债表、收益及收益分配表）、损益类期末结转至「321 本年收益」。
> - 同时允许：不存在的交易可不设科目；可自行增设科目；可自行设置明细科目。
> - **因用户明确不受该制度约束，以上均不作为本项目需求。**

**Q6. 记账方法？**
A: **先做流水账（单式），但要预留升级到复式的可能性。**
→ 后续细化为**明确不预留**。见决策记录 D1。

**Q7. 报送要求？**
A: **完全自用，谁都不给。** 不报送、不公开、不进监管平台。

**Q8. 成功标准？**
A: **记账人愿意持续用，Excel 停用。**
→ 可验证的替代指标见第 5 轮 Q4。

## 第 1 轮 · 用户与场景

**Q1. 有哪几类使用者？**
A: **只有一类——唯一的记账人。** 无角色划分。

**Q2. 典型使用过程？**
A: **每天随手记，一次几笔，在手机上记。**

**Q3. 需要登录吗？什么角色？**
A: **需要简单账号 + 密码。** 单人，无角色体系。

**Q4. 单人还是多人？**
A: **单人。** 不做协作、不做共享账本、不做权限系统。

**Q3. 每功能的输入 / 输出 / 异常**（**定稿**）

| 功能 | 输入 | 输出 | 异常与边界 |
|---|---|---|---|
| **M1 记一笔** | 日期（默认今天）、方向（收/支）、金额、二级科目（**必选，仅列启用中的**）、摘要（可选） | 一条流水（状态 = 已录入）；列表按日期倒序 | 金额 ≤ 0 → 拒绝并提示原因；未选科目 → 拒绝；**未来日期 → 允许但提示**；重复提交 → 前端按钮禁用 + 后端幂等键 |
| **M1 汇总** | 日期区间（默认本月） | 一级小计 + 可展开的二级小计 + 收入合计 / 支出合计 / 结余 | 区间内无数据 → 空状态；**区间颠倒 → 自动交换并提示**；**已作废流水不计入** |
| **M2/M3 科目管理** | 名称、层级（一级/二级）、父科目（二级必选） | 科目树 | 同级重名 → 拒绝；**未被引用 → 可删除**；**已被引用 → 拒绝删除，提示可停用**；**二级科目不允许改挂到别的一级**；停用已引用科目 → 提示「将影响 N 笔流水」 |
| **M4 筛选搜索** | 日期区间、科目、摘要关键字、金额范围 | 过滤后的流水 + **当前筛选条件下**的小计 | 无结果 → 空状态；区间颠倒 → 自动交换并提示；**已作废流水默认隐藏，可切换显示** |
| **M5 导出** | 当前筛选条件 + 内容（流水 / 汇总 / 两者）+ 格式（CSV / xlsx） | `.csv` 或 `.xlsx` 文件 | 结果为空 → 禁止导出并提示；生成失败 → 提示重试；**大数据量 → 流式生成，不限制范围** |

**Q4. 功能依赖关系**

```
M2 一级科目管理 ─┐
                 ├─→ M1 记一笔 ─→ M1 流水列表 ─→ M4 筛选搜索 ─→ M5 导出
M3 二级科目管理 ─┘                     │
                                      └─→ M1 按科目汇总 ─────→ M5 导出
```

- **科目管理是绝对前置项**：没有科目就无法归类，M1 无法工作。
- M5 依赖 M1 的汇总结果，不独立产出数据。

## 第 3 轮 · 数据与状态

**Q1. 核心实体与关系**

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `user` | 账号、密码哈希 | 唯一记账人 |
| `category` | `name`、`level`(1/2)、`parent_id`、`status`(启用/停用)、`balance_type`(余粮型/花费型)、`opening_balance_cents`(期初余额)、`include_in_reconciliation`(参与勾稽) | **严格两级，一级与二级均可自定义**。二级必有一级。详见 D6 |
| `transaction` | `date`、`direction`(收/支)、`amount_cents`、`category_id`(指向二级)、`note`、`status`(已录入/已作废) | 一条**收支**流水（涉及银行存款） |
| `transfer` | `date`、`note`、`source_category_id`、`source_amount_cents`、`status`(正常/已作废) | 一笔**转账**（1 转出 → N 转入，不涉及银行存款）。见 D7 |
| `transfer_leg` | `transfer_id`、`category_id`、`amount_cents` | 转账的转入明细行 |
| `change_log` | 实体类型、实体 ID、改前值、改后值、时间 | 变更留痕 |
| 资金账户设置 | `bank_opening_balance_cents` | 银行存款期初余额，系统配置项（非科目） |

> ⚠️ 每笔流水**必须**关联科目，不存在「无科目」的流水 —— 否则资金勾稽断裂。

**Q2. 数据来源？**
A: **纯手工录入。** 无第三方接口，无文件导入，历史 Excel 不迁移。

**Q3. 留存策略？**
A: **定时自动备份 + 一键恢复。**
→ 补充约束：**备份目标不应与数据同盘**（同盘备份对 NAS 盘故障无效）。

**Q4. 状态机**

`category` 生命周期：

```
   ┌──────────────────────────────────────────────┐
   │                   启用                        │
   └──────────────────────────────────────────────┘
     │                    │                    ▲
     │ 未被任何流水引用     │ 已被引用            │ 可重新启用
     ▼                    ▼                    │
   直接删除           ┌─────────┐              │
                     │  停用    │──────────────┘
                     └─────────┘
                  不出现在录入下拉框
                  历史流水与报表仍归属它
```

`transaction` 生命周期：

```
   录入 → ┌─────────┐ ──编辑──→ ┌─────────┐   （每次编辑写 change_log）
          │ 已录入  │           │ 已录入  │
          └─────────┘ ←──────── └─────────┘
               │
               │ 作废（可撤销）
               ▼
          ┌─────────┐
          │ 已作废  │  不计入任何汇总；记录保留、可查
          └─────────┘

   ⚠️ 任何状态都不可物理删除
```

**Q1. 技术栈硬约束？**
A: **必须 Docker 部署 + 低内存占用。**
→ 会筛掉 JVM 系及内存开销大的运行时。具体选型在 Step 2 展开。

**Q2. 部署在哪里？**
A: **局域网 / NAS**，家里或办公室。
→ 连带影响：出门无法记账（除非内网穿透）；登录仍需保留（内网不等于可信）。

## 决策记录

### D0 · 数据不可变策略总纲

用户在所有相关取舍上一律选择**可追溯优先**。这是贯穿全局的原则，后续所有涉及数据变更的设计都应遵守。

| 对象 | 可新建 | 可编辑 | 可删除 | 可作废 / 停用 |
|---|:---:|:---:|:---:|:---:|
| 一级科目 | ✓ | 名称可改 | **仅未被引用时** | ✓ 已引用可停用 |
| 二级科目 | ✓ | 名称可改；**不可改挂** | **仅未被引用时** | ✓ 已引用可停用 |
| 流水 | ✓ | ✓（**自动留痕**） | **✗ 任何状态都不可** | ✓ 作废（**可撤销**） |

| 项 | 内容 |
|---|---|
| 放弃的方案 | 允许自由删除 / 允许级联删除 / 允许二级科目改挂 |
| 决策理由 | 台账的价值在于经得起回头查。物理删除与静默改挂都会破坏历史口径 |
| 已知代价 | 数据只增不减，需要「停用」与「作废」两个状态作为出口 |

### D1 · 记账模型：采用简单流水表，不预留复式

| 项 | 内容 |
|---|---|
| **决策** | **单式流水表（`transaction` 单表），不为复式记账预留数据结构** |
| 放弃的方案 A | 底层按「凭证 + 分录」建模，MVP 每笔流水 = 一凭证两分录，UI 仅暴露业务科目（**前台推荐方案**） |
| 放弃的方案 B | 一开始就做完整复式（借贷平衡、科目余额、期末结转、法定报表） |
| 决策理由 | 用户明确选择 MVP 最快最简；方案 B 工作量约为所选方案的 2.5-3 倍 |
| **已知代价** | 未来若升级复式需：① 新建凭证/分录表 ② 迁移历史 transaction（每笔补一条对方分录）③ 重写汇总查询 ④ 重写报表。**约等于重做数据层** |
| 可逆性 | 可逆，代价随数据量线性增长 |

### D2 · 导出：CSV 与 xlsx 两者都要

| 项 | 内容 |
|---|---|
| **决策** | M5 同时提供 CSV（数据交换）与 xlsx（给人看，带格式） |
| 放弃的方案 A | 只做 CSV —— 与「导出后不用手工加工」的验收标准直接冲突 |
| 放弃的方案 B | 只做 xlsx —— 缺少机器可读的交换格式，数据仍有一定锁死风险 |
| 放弃的方案 C | 先只做 CSV，格式以后再说 —— 会让验收标准暂时无法验证 |
| 已知代价 | xlsx 生成库会增加包体与**运行时内存占用**，与「低内存」硬约束有轻微冲突 → 由 D5 缓解 |

### D3 · 错账处理：允许编辑 + 自动留痕

| 项 | 内容 |
|---|---|
| **决策** | 允许直接编辑流水，但自动写入 `change_log`（改前值、改后值、时间） |
| 放弃的方案 A | 直接编辑不留历史 —— 改错查不回来 |
| 放弃的方案 B | 不能编辑只能作废重记 —— 最规范，但交互啰嗦，单人自用不划算 |
| 放弃的方案 C | 直接删除 + 重记 —— 彻底丧失可追溯性 |
| 已知代价 | 多一张 `change_log` 表 + 写入逻辑，成本很低 |

### D4 · 出口机制：科目「停用」+ 流水「作废」

> **背景**：D0 的三条「不允许」（已引用科目不可删、流水不可删、二级科目不可改挂）组合后会产生两个死锁，
> 本决策是补上出口，不是推翻 D0。

**死锁 A** — 科目废弃后永久残留：业务调整时（如「办公费」应从「管理费用」改挂到「行政支出」），
因不可改挂只能新建，旧科目又被流水引用而不可删 → 科目列表越积越多废弃项。

**死锁 B** — 误记/重复的流水无法清理：重复录入多出来一条，不可删除又无法归零 → 汇总永远对不上。

| 项 | 内容 |
|---|---|
| **决策** | ① `category` 增加「启用/停用」状态：停用后不出现在录入下拉框，历史流水与报表仍归属它<br>② `transaction` 增加「已作废」状态：不计入任何汇总，记录保留、可查、**可撤销** |
| 放弃的方案 A | 不加出口，废弃项就留着 —— 科目列表长期失控 |
| 放弃的方案 B | 已引用科目要求先手动逐笔改流水才能删 —— 最干净但操作极烦 |
| 放弃的方案 C | 允许删除但仅限当天记录 —— 实用折中，但与「可追溯优先」不一致 |
| 与 D0 的关系 | **不冲突**。停用与作废都不是删除，历史口径与可追溯性完整保留 |
| 会计对应 | 「作废」对应会计上的**冲销**概念 |

### D5 · 导出实现：流式生成，不限制范围

| 项 | 内容 |
|---|---|
| **决策** | M5 采用**流式生成**，单次导出不限制时间跨度 |
| 放弃的方案 A | 不做特殊处理（一次性生成） —— 按当前规模（一年约 1100-1800 条）实际足够，是最简方案 |
| 放弃的方案 B | 限制单次导出跨度（如 ≤12 个月）—— 给使用添麻烦 |
| 放弃的方案 C | 流式 + 超阈值提示分批 —— 对当前规模属过度设计 |
| 决策理由 | 用户在了解规模后仍选择流式。成本可控，且彻底排除未来 OOM 可能 |
| 副作用 | 缓解 D2 中 xlsx 生成与「低内存」硬约束的冲突 → **关闭风险 R2** |

### D6 · 余额模型：银行存款为基准 + 科目带类型余额

> **来源**：用户在 PRD/设计方案评审阶段提出的新需求，推翻了原「单一隐含资金池」的设计。
> 原始表述：「按银行存款的收支记账，记账时关联的科目相应的增加减少。同时，在设置科目时，可以自定义余额。」

**模型定义**

| 概念 | 定义 |
|------|------|
| 银行存款 | 唯一真实资金账户，系统配置项，有独立期初余额。**不是科目** |
| 科目余额 | `期初余额 + 该科目下的流水累计`，方向由科目类型决定 |
| **余粮型** | 收增支减。余额 = 期初 + 收 − 支。用于专项资金类、收入类（「还剩多少」） |
| **花费型** | 支增收减。余额 = 期初 + 支 − 收。用于支出类（「累计花了多少」，正数） |
| 期初余额 | 建科目时自定义的**期初余额**，之后只能由流水改变（用户选择，非「可随时改的当前余额」） |
| 参与勾稽 | 布尔开关。**仅余粮型科目可开启** |
| 未分配资金 | `银行存款余额 − Σ(参与勾稽的科目余额)`，即自有/可自由支配的部分 |

**验算表**（用户已确认此算法）

| 步骤 | 银行存款 | 修路款（余粮型·勾稽） | 办公费（花费型·不勾稽） | 专项资金合计 | 未分配 |
|---|---|---|---|---|---|
| 期初设置 | 100,000 | 30,000 | 0 | 30,000 | 70,000 |
| ① 收财政拨修路款 50,000 | 150,000 | 80,000 | 0 | 80,000 | 70,000 |
| ② 支修路工程款 20,000 | 130,000 | 60,000 | 0 | 60,000 | 70,000 |
| ③ 支办公用品 500（办公费） | 129,500 | 60,000 | **+500** | 60,000 | **69,500** |

**强制校验规则**

1. ⚠️ **只有余粮型科目可参与勾稽。** 已验算：若花费型科目参与勾稽，其正数余额会被二次扣减，
   导致未分配算错（129,500 − 60,000 − 500 = 69,000，正确值 69,500）
2. 每笔流水**必须**关联科目，不允许无科目流水
3. 已作废流水不计入任何余额
4. `Σ(参与勾稽科目的期初余额) ≤ 银行存款期初余额`，超出则未分配为负，需在设置时警告

| 项 | 内容 |
|---|---|
| 放弃的方案 A | 统一规则「收增支减」不分类型 —— 用户初选，但会导致支出类科目余额为负（办公费 −500），后改为带类型 |
| 放弃的方案 B | 「自定义余额 = 可随时修改的当前余额」—— 余额与流水对不上，时间一长不知哪个数准 |
| 放弃的方案 C | 「所有科目余额之和 = 银行存款余额」的强勾稽 —— 与「只有部分科目参与勾稽」矛盾 |
| 与 D1 的关系 | **不冲突**。本模型不含借贷平衡校验，不是复式记账，D1（不预留复式）继续有效 |
| 与「单一资金池」的关系 | **已推翻**。原设计资金池隐含、不做实体；现改为显式的银行存款配置项 + 科目带余额 |

### D7 · 科目间转入转出（转账）

> **来源**：用户在 D6 基础上追加的功能：「没有银行存款收支，科目与科目之间的转入转出。
> 可以实现同一笔金额可转出多科目。」用途经确认 = **专款调剂 + 期末结转，两种都有**。

**模型定义**

| 项 | 定义 |
|---|---|
| 转账 | 不涉及银行存款、不算收支的科目余额划转。**1 个转出科目 → N 个转入科目**，各自带金额，转出总额 = 转入总额 |
| 用途 1 | 专款调剂：余粮型资金科目间调拨（修路款 → 水利款） |
| 用途 2 | 期末结转：收支科目余额结转清零（经营支出 → 本年收益；经营收入 → 本年收益） |
| 余额影响 | 余粮型：`期初 + 收 + 转入 − 支 − 转出`；花费型：`期初 + 支 − 收 − 转出`（不得作转入方） |
| 勾稽影响 | 转账不改变银行存款；跨勾稽边界的转账改变未分配（专款转自有 / 自有转专款），属正常业务 |

**验算表**（用户已逐行确认）

科目：修路款(余粮·勾稽,期初3万)、水利款(余粮·勾稽)、经营收入(余粮·不勾稽)、经营支出(花费型)、本年收益(余粮·不勾稽)，银行存款期初 20 万。

| 步骤 | 银行存款 | 修路款 | 水利款 | 经营收入 | 经营支出 | 本年收益 | 未分配 |
|---|---|---|---|---|---|---|---|
| 期初 | 200,000 | 30,000 | 0 | 0 | 0 | 0 | 170,000 |
| ① 转账：修路款→水利款 2 万 | 200,000 | 10,000 | 20,000 | 0 | 0 | 0 | 170,000 |
| ② 收经营收入 6 万 | 260,000 | 10,000 | 20,000 | 60,000 | 0 | 0 | 230,000 |
| ③ 支水电费 4 万（经营支出） | 220,000 | 10,000 | 20,000 | 60,000 | 40,000 | 0 | 190,000 |
| ④ 结转：经营支出→本年收益 4 万 | 220,000 | 10,000 | 20,000 | 60,000 | 0 | 40,000 | 190,000 |
| ⑤ 结转：经营收入→本年收益 6 万 | 220,000 | 10,000 | 20,000 | 0 | 0 | 100,000 | 190,000 |

> ④⑤ 表明：期末结转不产生真实现金流动（钱在记收支时已进出银行），所以**银行与未分配均不变**。

**强制规则（用户已确认 R1-R6）**

# v0.3 变更（2026-09-03）· 多组织 + 资产科目 + 应收往来 + 预置科目

> 本版本是需求的一次结构性升级，覆盖并取代旧文中所有「单组织」「一个记账人」的前提。
> 冲突处以本变更内容为准。旧章保留供追溯。

## V1. 使用形态（取代旧「用户与问题」的单组织前提）

- **一套系统部署，多个集体经济组织各自注册使用**，各组织**独立记账、数据完全隔离**（无跨组织查看，无上级角色）。

## V2. 多组织与账号（新增决策 D9）

| 决策 | 内容 | 放弃的方案 |

| 隔离模型 | 单实例单库，所有业务表带 `org_id`，服务层强制按登录者组织过滤 | 每组织独立部署/独立库（运维重、无法统一升级） |

## V3. 资金模型扩展（新增决策 D10）

- 场景：上级拨付本金 → 投资（本金从银行转出但仍属于集体），每年收益按组织分配方案（5:2:3 等）由操作者自行决定金额与去向，**系统不做比例自动拆分**。
- 科目新增**资产型**（`kind='asset'`）：代表银行账户之外、仍属于本组织的资产（对外投资）。与现有「余粮/花费」余额类型正交：
  - 资产科目余额 = 累计投出 − 累计收回（只看存量，看"本金在外多少"）。
  - 资产科目不参与资金勾稽、不允许直接记收/支流水（只走资金划转）。
- 新增**资金划转**操作（`fund_move`）：`投资`（银行存款 → 资产科目）与`收回`（资产科目 → 银行存款），单事务原子，支持作废。
- **资金构成口径升级**：可用资金 = 银行存款 + Σ资产科目余额；未分配资金 = 可用资金 − Σ勾稽科目余额。银行存款余额 = 期初 + Σ收支 − Σ投资划转 + Σ收回划转。
- 验算基准（期初自有 200 万、拨本金 100 万、投出 60 万、年收益 10 万、523 分配）见会话确认表，作为回归用例。

## V4. 应收/欠款（新增决策 D11）

- 场景：投资收益**拖欠**、土地流转费**收缴不齐** → 需要按对象查出"谁欠多少"。
- 实体：`party` 往来对象（农户/单位）、`receivable` 应收单（分类：流转费 / 投资收益 / 其他）、`receipt` 核销记录（分次收款；核销方式：现金入账 / 抵销）。
- **收款自动入银行账**：现金收款生成一条银行收入流水（可挂到应收单预设的收入科目），应收模块与银行账同步，不重复记账。
- **抵销**：可用某人应收欠款抵其分红/福利应付款（核销方式 = 抵销，关联一条发放支出流水，不新增现金流水）。
- 欠款呈现：独立**「往来」页**（底部导航第 5 个 tab），按对象与类别查看欠款余额。

| 审核 | 每次测试/验收需**认真逐项审核**，覆盖真实后端与 mock 之间的行为落差，**防止功能丢失**（如 532 分配曾因仅在 mock 实现而被误判为可用）。 |
| 前置 | 任何新版本发布前，须以真实 Go 后端 + 前端构建产物做端到端回归确认全量功能仍可用，再进入交付。 |
| 关联 | 承接 D13：交付产物及其验收均已切换到真实运行链路。 |
